# 基础局内体验更新：收集口径

建立时间：2026-09-16。适用于现有七款游戏及以后确认官方来源的新游戏。首批以 Free Fire（FF）验证口径，属于抽样整理，不代表 2023—2026 连续历史已收全。

用户关注的是：**在原有模式内，哪些内容改变了玩家搜刮、移动、交战、争夺、救援和读取信息的方式。** 不要求存在一个新模式名称，也不要求单独匹配入口。

## 收集分类

| 分类 | 内部值 | 重点记录 |
|---|---|---|
| 地图与 POI | `map_poi` | 新地图的玩法结构、老地点重做、建筑/掩体/高差/路线/视线改造、可破坏场景 |
| 地图交互物 | `map_interactable` | 军械库、资源终端、占领装置、复活装置、机关、动态争夺点 |
| 道具与装备 | `equipment` | 新武器、新投掷物、新装置、配件、治疗道具及使用方式重做 |
| 移动与转点 | `traversal` | 滑轨、滑索、传送、载具、跳伞、攀爬、加速和移动限制 |
| 资源与经济 | `economy_loot` | 物资分布、空投、商店、局内货币、购买限制、装备生成与成长 |
| 救援与返场 | `revive_teamplay` | 倒地救援、复活条件、返场装备、队伍资源共享及配合规则 |
| 战斗与对局规则 | `combat_rules` | 安全区、伤害/护甲机制、角色能力重做、携带槽位、重要武器定位调整 |
| 局内操作与信息 | `in_match_usability` | 小地图、标记、提示音、敌我识别、交互反馈、拾取与操作冲突修复 |

同一条可有多个分类，首项为主分类。这里只是“更新对象”维度；BR、大战场、爆破、搜打撤、PVE、其他（休闲）仍按现有 `gameplayTypes` 归类。例如 FF 枪王对决继承本站 `casual`，不能因其有购买阶段就归为爆破。

## 收录层级与边界

- **独立案例**：有可解释的新决策或行为变化，例如新增通路、可争夺装置、装备槽位拆分、返场条件重做。单条小型交互改进也可收，不要求规模很大。
- **版本摘要**：普通伤害/后坐力小调、价格微调、同类小地图与交互优化按版本归并；若数值变化改变了武器定位、携带上限、资源循环等，再单独拆卡。不是一律忽略数值调整。
- **活动内更新**：活动中的 POI、道具和局内机制也能收，但标 `event_overlay` 并关联原活动卡；不能因为出现在 BR 中就称为常驻更新。纯主题换色、皮肤及装饰不单独收。
- **本范围之外**：大厅、商城付费、通行证奖励、纯外观、赛事宣传、社交展示、匹配/段位结算等局外内容。训练场更新可留拓展候选，不与常规对局更新混计；卡顿或 BUG 仅在明显影响局内操作、可读性、路线或对战公平时纳入。

公告中的“优化”属于官方意图，不自动证明体验变好。资料用“更新/调整”描述事实；`designObservation` 明确写为设计推断，不写成已经验证的玩家效果。

## 单条记录方式

一条记录对应一个“对象在某版本发生的变化”，不整篇复制补丁。同一对象的后续变化继续用相同 `objectKey`，通过 `previousUpdateIds` 串联，保留历史规则；不要把 2023 年的规则当成今天的现状。互相独立的 POI 可拆开；同一系统内需要一起理解的调整可合并。

建议阅读结构：标题 → 适用模式/地图 → 改前与改后 → 玩家决策变化 → 设计观察 → 日期与官方来源。

当前队列 `data/core-updates.json` 为 JSON 数组，字段约定如下：

| 字段 | 含义 |
|---|---|
| `id`、`objectKey` | 独立版本记录 ID；可跨版本追踪的对象 ID |
| `contentKind` | 固定 `core_update`，代表基础体验资料类别，不代表常驻 |
| `title`、`game` | 中文标题、稳定游戏标识 |
| `categories`、`changeType` | 上述分类；`addition` / `rework` / `tuning` / `qol` / `removal` |
| `updateScope`、`duration` | `core` / `event_overlay` / `unknown`；`permanent` / `limited` / `unspecified` |
| `gameplayTypes`、`affectedModes`、`mapNames` | 核心玩法、实际适用模式、地图及点位；未明确的范围写入备注 |
| `sourceModeIds`、`sourceMapIds` | 只关联已存在的模式/地图 ID；无对应父卡可为空，不编造父记录 |
| `before`、`after` | 原文明确的改前与改后；改前未说明可为空 |
| `playerImpact`、`designObservation` | 对玩家行为的推断；可复用的设计观察，与事实分栏 |
| `versionLabel`、`publishedDate` | 版本名（没核实编号就用公告日期）、公告日期 |
| `effectiveDate`、`effectiveDateStatus` | 实际/预定生效日期；`confirmed` / `scheduled` / `unverified`；后两者不得显示为已确认上线 |
| `timingNote`、`scopeNote` | 日期证据、模式/区域限制及未确认部分 |
| `sourceUrl`、`sourceHeading` | 官方原文和对应小节标题；英文来源标题用于回查，不作为中文正文 |
| `previousUpdateIds` | 同一对象的既有历史版本关联，首次可为空 |
| `reviewStatus`、`publicationStatus`、`reviewedAt` | `source_verified` 表示本条机制已查原文；`staged` 表示待接入，`ready` 表示允许前端展示；审阅日期 |
| `imageUrl`、`imageSource`、`imageStatus` | 已核实为 `verified_official`，未核实为 `pending_official_asset`；保留原始地址 `imageAssetSourceUrl`、出处页 `imageSourcePageUrl`、范围 `imageScope`（specific / section / version）及审阅日期 |

`source_verified` 不代表图片、精确生效日或今日仍有效均已确认。没有截止日期时用 `unspecified`，不用 `permanent`。基础更新不直接套用模式的 `isLtm`：临时道具不等于限时模式。

## 后续每轮采集流程

1. 同时阅读现有 `data/mode-source-coverage.json` 和新增 `data/core-update-source-coverage.json`。先查最新版本，再逐批回填历史。
2. 检查完整官方补丁正文，至少覆盖地图、模式内规则、武器/道具、角色技能、资源/商店、复活、载具和局内操作章节，不只搜“新模式”。
3. 对条目记为：独立案例、版本摘要、已收录、活动关联、局外排除或待核实。旧审计的 `system-only` 需重新评估；同一 URL 允许产生多条不同对象更新。
4. 按游戏 + 对象 + 版本/日期 + 适用范围去重，并检查 `modes.json` 中是否已有父案例。不要因同页另有联动而把整页都判为限时。
5. 原文未写改前状态时不推演历史；精确日期以明确上线说明为准。预告到期后仍需复核，不能按系统时间自动改成已上线。
6. 写中文摘要并分别保存事实和推断。机制图片只采用可核实的官方素材；POI 改造可优先补官方前后对比图。
7. 更新本轮检查的文章、小节、实际收录 ID、剩余候选和下一批范围。模式历史覆盖率不能复用作基础更新覆盖率。
